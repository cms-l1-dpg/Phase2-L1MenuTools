# Object Performance Tools
  
  The object performance tools allow the user to produce
  matching efficiency, turn-on curves, and scaling plots for
  the various L1 objects, and for the Phase-2 HLT objects of the L1+HLT nanos
  (`configs/V50nano/object_performance/hlt_*.yaml`, objects in `configs/V50nano/objects/hlt.yaml`;
  see [objects](objects.md#hlt-objects)).
  The definition of each object to be tested is detailed in
  this [TWiki page](https://twiki.cern.ch/twiki/bin/view/CMS/PhaseIIL1TriggerMenuTools).

  A detailed description of each step, together with instructions on how to set up the
  configuration files for the cache and plotting steps, is given in
  [the Wiki pages](https://github.com/cms-l1-dpg/Phase2-L1MenuTools/wiki).

  The following presents the commands to be run to produce the standard set of validation
  plots (cf. [these slides](https://twiki.cern.ch/twiki/pub/CMS/PhaseIIL1TriggerMenuTools/Phase2Menu_validation123x-3.pdf)).

## Caching the NTuple trees

  **Note:** When running on lxplus, usually the cache files will already
  be present in the symliked directory included with the repo.

  In order to run the next steps, the object
  `TTrees` from the L1NTuples need to be cached
  as `awkward` arrays saved into `.parquet` files.
  This is done by running:

  ```
  cache_objects <path_to_config>
  ```

  An example for a caching config can be found at `configs/V29/caching.yaml`.
  The output of this step is saved to `cache`.
  This step needs to be run only once per configuration (unless changes in the input
  L1 ntuples occur) and the `.parquet` files generated by the code can be
  used for all the subsequent steps of the workflow, without having to open the
  `.root` files and load the objects every time the framework is run.

## Efficiency and Scalings
  To produce matching efficiencies, turn-on curves, and L1 scalings run

  ```
  object_performance <path_to_config>
  ```

  The production of the scalings is a prerequisite for the generation of
  offline rate plots as well as the rate table. It is possible to use
  wildcards (e.g. `*_trigger.yaml`) to run multiple configs in succession.

### Reference config files

  Default configuration files are contained in `configs` and should be used as
  templates for custom configurations.

  The points used for the calculation of the scalings correspond to the list of
  threshold cuts defined in
  [`scaling_thresholds`](https://github.com/cms-l1-dpg/Phase2-L1MenuTools/blob/main/configs/scaling_thresholds.yaml).

  The outputs will be written to the `outputs/<VERSION>` directory,
  where `<VERSION>` is the version of the ntuples used for the plots as specified
  in the `.yaml` config file (more details on the config file are given below).
  In the current version of the code, the plots will be saved in three folders under `outputs/<VERSION>`:

  * `distributions`: plots of the distributions (histograms) used to compute the efficiencies. For each efficiency curve plotted, these plots depict the distributions used for as numberator and denumerator in the computation of the efficiencies.

  * `turnons`: plots of the matching efficiencies and L1 turn-on efficiency curves.

  * `scalings`: plots of the scalings, i.e. position of the turnon point (often 95% location) as a function of different threshold cuts on L1 objects.

### Matching + threshold (trigger) efficiencies

  For configurations with `match_test_to_ref: True` the efficiency definition
  depends on the threshold:

  * no `thresholds` given (matching efficiency):
    `N(ref matched to test) / N(ref)`
  * `thresholds` given (turn-on / threshold efficiency):
    `N(ref matched to test with L1 pT >= threshold) / N(ref matched to test)`

  To obtain the combined *matching + threshold* (trigger) efficiency, i.e.
  `N(ref matched to test with L1 pT >= threshold) / N(ref)`,
  add `matching_and_threshold: True` to the plot configuration:

  ```yaml
  ElectronsTriggerBarrel_wMatching:
    sample: DYLL_M50
    version: V50nano
    match_test_to_ref: True
    matching_and_threshold: True
    ...
    thresholds: [10, 20, 30, 40]
  ```

  The plateau of these curves corresponds to the matching efficiency.
  Since they generally do not reach 100%, no `scalings` should be configured
  for such plots. The denominator is filled with the reference object's
  `x_arg`, the numerator with the reference field named by the test objects'
  `x_arg`, so the two must be the same (an error is raised otherwise).
  Examples can be found in
  `configs/V50nano/object_performance/*_trigger_wMatching.yaml`
  (and `configs/V43nano/object_performance/` for the older version).

  **Efficiency vs eta (or any other variable) with a pT threshold.** By default the threshold
  is applied to the test objects' `x_arg`, i.e. the plotted variable. Set
  `threshold_field: "pt"` to apply it to the test pT instead, while plotting vs the reference
  `x_arg` (all `x_arg`s set to `"eta"`); restrict the reference pT to the plateau with an event cut:

  ```yaml
  HLTMuonsTrigger_Eta_Pt30ToInf_wMatching:
    match_test_to_ref: True
    matching_and_threshold: True
    threshold_field: "pt"
    reference_object:
      object: "GenPart"
      x_arg: "eta"
      cuts:
        event: ["{pt} > 30", ...]
    test_objects:
      hltMuon:default: "eta"
    thresholds: [24]
  ```

  Examples: `configs/V50nano/object_performance/hlt_*_eta.yaml`.

### Combined L1 x HLT object efficiency (`l1_seed`)

  The optional `l1_seed` block of a matched turn-on adds the L1 seed requirement to HLT test objects:
  a reference object counts in the combined numerator only if it is matched to the HLT object passing
  the HLT threshold **and** to an L1 seed object passing the L1 threshold. This is the object-level
  analogue of the path efficiency (`path_efficiency`, next section). Example
  (`configs/V50nano/object_performance/hlt_muon_l1seed.yaml`):

  ```yaml
  HLTMuonL1Seed_IsoMu24:
    sample: DYLL_M50
    version: V50nano
    match_test_to_ref: True
    matching_and_threshold: True          # denominator: all reference objects
    reference_object:
      object: "GenPart"
      x_arg: "pt"
      cuts:
        object: ["(({statusFlags}>>7)&1) == 1", "abs({pdgId}) == 13", "abs({eta}) < 2.4"]
    test_objects:
      hltMuon:default: "pt"
    l1_seed:
      object: "L1gmtTkMuon:VLoose"        # L1 object (id / eta range as for test objects)
      threshold: {barrel: 20.2, overlap: 20.3, endcap: 20.3}   # L1 *online* pT, or one number
      # match_dR: 0.1                     # default: the L1 object's match_dR
      # apply_to: [hltMuon:default]       # default: all hlt* test objects
      # label: "pSingleTkMuon22"          # legend; default: L1 object label and thresholds
    thresholds: [24]                      # HLT thresholds, as usual
    ...
  ```

  Several L1 conditions are OR-ed with `objects` (e.g. the seeds of `HLT_Ele32_WPTight`,
  `hlt_electron_l1seed.yaml`):

  ```yaml
    l1_seed:
      label: "IsoTkEle28 OR TkEle36 OR EGEle51"
      objects:
        - {object: "L1tkElectron:Iso",   threshold: {barrel: 20.9, endcap: 20.9}}
        - {object: "L1tkElectron:NoIso", threshold: {barrel: 27.4, endcap: 26.7}}
        - {object: "L1tkPhoton:NoIso",   threshold: {barrel: 40.1, endcap: 39.2}, match_dR: 0.15}
  ```

  **L1 requirement.** Per reference object: some L1 seed object (after its id cuts) within `match_dR`
  with pT **>** threshold (strictly, as the P2GT emulator, which cuts hwPt > floor(thr / LSB); for pT
  in units of the LSB this is the same as pt > thr). Taking *any* passing L1 object within `match_dR`
  is, for a single threshold, the same as taking the highest-pT L1 object within `match_dR` (as for the
  test objects) and cutting on it. The threshold is a number or a `{region: threshold}` map over the
  `eta_ranges` of the L1 object's config (|eta| in [low, high)); L1 objects outside the listed regions
  never pass. The thresholds are **online** (nano) pT values: for a GT seed take the offline threshold
  of the seed and invert the GT scalings, online = (offline - offset) / slope, with the scalings of the
  P2GT menu (`L1Trigger/Configuration/python/Phase2GTMenus/SeedDefinitions/step1_2024/l1tGTObject_scalings.py`
  in CMSSW_17_0_0_pre6, rounded to 0.1 GeV as in `get_object_thrs`). These are not always the menu-tools
  v0p0 scalings (e.g. IsoTkEle28: 20.9 GeV with the GT scalings, 22.8 / 22.2 GeV with v0p0). The
  values in the `hlt_*_l1seed.yaml` configs reproduce the GT emulator bits event by event (single-object
  seeds; for pDoublePuppiTau52_52 with both legs and dR > 0.5), see the comments in the configs.

  **Curves** (in the plot and the JSON, next to the configured test objects):

  | key | numerator | denominator |
  |---|---|---|
  | `<test obj>` (e.g. `hltMuon:default:inclusive`) | unchanged: matched to the HLT object with pT ≥ HLT threshold | unchanged |
  | `L1seed` | matched to an L1 seed object passing the L1 threshold (does not depend on the HLT threshold) | all reference objects (`matching_and_threshold: True` or no threshold); otherwise the reference objects matched to an L1 seed object of any pT |
  | `<test obj>+L1seed` (e.g. `hltMuon:default:inclusive+L1seed`) | `<test obj>` numerator AND the L1 requirement on the same reference object | that of `<test obj>` |

  Legend labels: `L1 seed: <label>` and `<HLT label> ∧ L1 seed`; markers: squares for the seed, open
  triangles for the combination. The JSON entries have the usual structure (`label`, `efficiency`,
  `efficiency_err`, `xbins`, `err_kwargs`). Without `l1_seed` nothing changes. Use
  `matching_and_threshold: True`: with it, the three curves share the denominator (all reference
  objects) and L1 ∧ HLT ≤ min(L1, HLT) in every bin. `threshold_field` works as for the test objects
  (the L1 threshold is always on the L1 pT).

  **Limitations.**
  * Multi-object seeds are applied per object (one leg): e.g. for `L1_pDoublePuppiTau52_52`
    (`hlt_tau_l1seed.yaml`) the reference tau must be matched to an L1 tau passing one leg; the other leg
    and the seed's dR / dz / mass conditions are not required. Use `path_efficiency` for the full
    path. Cross seeds (e.g. muon + tau) can only be given by the leg of the plotted object.
  * Event-level effects are not included: the HLT bit can fire on another object of the event (e.g. the
    other muon in DY), and HLT selections that are not in the nano (isolation of IsoMu24, HGCAL e/gamma
    variables) are missing or approximate in the HLT test objects.
  * Some HLT collections are stored only in events with an L1 seed (`hltMuon`: L1 tkMuon,
    `hltHpsPFTau`: L1 tau seed), so their HLT-only curves already contain part of the L1 requirement.
  * Only for matched turn-ons (`match_test_to_ref: True`), not for `iso_vs_efficiency`.

  Configs: `configs/V50nano/object_performance/hlt_{muon,electron,tau,jets}_l1seed.yaml` (V50nano_170pre6HLT).
  Tests: `menu_tools/object_performance/tests/test_l1_seed.py`.

### Split by reference categories (`split_by`)

  The optional `split_by` block splits matched efficiencies (and resolutions, next section) by
  categories of a field of the reference object, e.g. the generator decay mode of the visible gen
  tau. It works for matching efficiencies, turn-ons (also with `matching_and_threshold` and
  `threshold_field`, e.g. efficiency vs eta) and the `l1_seed` curves. Example
  (`configs/V50nano/object_performance/hlt_tau_matching_dm.yaml`):

  ```yaml
  HLTTausMatchingBarrel_DM:
    sample: HHTo2B2Tau
    version: V50nano
    match_test_to_ref: True
    reference_object: {object: "GenVisTau", x_arg: "pt", ...}
    test_objects:
      hltHpsPFTau:default: "pt"
      L1nnPuppiTau:default: "pt"
    split_by:
      field: status                 # reference field (name without the `GenVisTau_` prefix)
      categories:                   # legend label -> values of the field (disjoint)
        "1-prong": [0]
        "1-prong + $\\pi^0$s": [1, 2]
        "3-prong": [10]
        "3-prong + $\\pi^0$": [11]
      # name: DM                    # file-name tag, default `by_<field>`; "" for none
      # layout: per_object          # per_object (default) or per_category
      # summary_range: [40, 150]    # x range of the integrated efficiencies (default: binning)
    ...
  ```

  Each category is the same efficiency restricted to the reference objects of that category, in the
  numerator and the denominator (for `matching_and_threshold` all reference objects of the category,
  for pure threshold efficiencies the matched ones). Reference objects in no category ("other") are
  only in the inclusive curve. The usual (inclusive) plot, JSON and distributions are unchanged.
  In addition, in `outputs/<version>/object_performance/turnons/` (`<tag>` = `_<name>`):

  * `<plot><tag>_<curve>_<threshold>_<version>.{png,pdf,json}` (`layout: per_object`): one plot per
    curve (test object, `L1seed`, `<test obj>+L1seed`; `:` written as `-`, `+` as `_`), with the
    inclusive curve (black, "All") and one curve per category; the legend gives each category's
    share of the denominator. With `layout: per_category`: `<plot><tag>_<category>_...`, one plot
    per category with all curves.
  * `<plot><tag>_fractions_<threshold>_<version>.json`: the category table: `reference` (counts and
    fractions of all reference objects after the reference cuts, including `other`), and per curve
    and category (`inclusive`, the categories, `other`): `n_den`, `n_num`, `fraction` of the
    denominator, and the `efficiency` with Clopper-Pearson `err` integrated over `summary_range`.

  The per-plot JSONs have the usual structure (keys `inclusive` and the category names, or the curve
  keys for `per_category`). Only for matched turn-ons (`match_test_to_ref: True`), not for
  `iso_vs_efficiency` or `trafo` references. Without `split_by` nothing changes.

  **Tau decay modes.** `GenVisTau_status` is the generator decay mode of the visible tau
  (`GenVisTauProducer`, `JetMCTagUtils::genTauDecayMode`, stored as `reco::PFTau::hadronicDecayMode`):
  0 = 1-prong, 1 = 1-prong + 1 π0, 2 = 1-prong + 2 π0, 10 = 3-prong, 11 = 3-prong + 1 π0,
  15 = other (neutral hadrons such as K0, ≥ 3 π0, 3-prong + ≥ 2 π0, 5-prong). In HH → bbττ
  (V50nano_170pre6HLT, gen vis. pT > 20 GeV, |η| < 2.1): 14.6% / 39.5% / 15.4% / 16.1% / 8.0% / 6.3%.
  Configs: `configs/V50nano/object_performance/{hlt_tau,tau}_*_dm.yaml` (generated from the
  configs without `_dm`; plot names + `_DM`, no scalings). Tests:
  `menu_tools/object_performance/tests/test_split_by.py`.

## Response and resolution

  A plot entry with a `resolution:` block produces pT, eta and phi response / resolution plots
  instead of efficiencies (`object_performance <config>` dispatches it; `--version` works as usual):

  ```
  object_performance configs/V50nano/object_performance/tkmuon_resolution.yaml --version V50nano_170X1026
  ```

  Reference configs: `{electron,photons,tkmuon,tau,jets,met}_resolution.yaml` in
  `configs/V50nano/object_performance`.

  **Pairs.** With `match_test_to_ref: True`, the reference cuts, the test-object cuts and the matching
  are those of the matching efficiencies: in each event the leading reference object (after the cuts)
  is paired with the highest-pT test object within `match_dR`. Unmatched references are dropped
  (that is the efficiency). Without `match_test_to_ref` the comparison is event by event without
  matching, for energy sums: `GenMET` vs `L1puppiMET`, or gen HT (`trafo: HT`) vs L1 HT.

  **Quantities.** `pt`: response $p_T^{L1}/p_T^{ref}$ (for sums: L1 value / reference value);
  `eta`: $\eta^{L1}-\eta^{ref}$; `phi`: $\phi^{L1}-\phi^{ref}$ wrapped to $[-\pi, \pi)$.
  In each bin: the median, and the effective resolution $\sigma_{eff}$ = half of the 16–84% interquantile
  range (divided by the median for `pt`), with the counts and distribution-free uncertainties from
  the order statistics (the rank of a $p$-quantile fluctuates by $\sqrt{np(1-p)}$; the 16% and 84%
  errors are added in quadrature, neglecting their correlation).

  ```yaml
  MuonsResolutionBarrel:
    sample: DYLL_M50
    version: V50nano
    match_test_to_ref: True
    reference_object: {...}            # as in the *_matching.yaml configs
    test_objects:
      L1gmtTkMuon:default:barrel: "pt"
    resolution:
      variables: [pt, eta, phi]        # default [pt, eta, phi]; event-level: [pt, phi]
      vs:                              # binning variables; default: pt with the top-level `binning`
        pt: {edges: [3, 5, 10, 20, 50, 100]}       # reference pT ({min, max, step} also works)
        eta: {min: -2.4, max: 2.4, step: 0.2}      # reference eta (abseta: |eta|)
        pu: {edges: [150, 180, 200, 220, 260]}     # pileup, from the `Pileup` parquet
      response_binning:                # optional: per-bin response distributions for these variables
        pt: {min: 0, max: 2, step: 0.04}
      pu_variable: nPU                 # Pileup field (default nPU; nTrueInt is constant 200 in Spring24)
      min_entries: 20                  # bins with fewer pairs are not reported (default 20)
      min_ref: 0                       # event-level only: keep reference value > min_ref
  ```

  Each `vs` entry can also carry a `label` for the x axis. The pileup binning reads
  `<version>_<sample>_Pileup.parquet` (one row per event, row-aligned with the object parquets;
  cache the nano `Pileup` table to get it); if it is missing the `pu` binning is skipped with a warning.
  The event-level phi response needs a `phi` field in both reference and test (e.g. not `L1TrackMET`).

  Outputs, in `outputs/<version>/object_performance/resolution/`:

  * `<plot>_<var>_vs_<vs>_<version>.{png,pdf,json}`: median (top) and resolution (bottom) vs `<vs>`,
    all test objects overlaid; the json has per object `xbins`, `edges`, `n`, `median(_err)`,
    `q16`, `q84`, `resolution(_err)`, `mean`, `std`;
  * `<plot>_<var>_vs_<vs>_dist_<version>.{png,pdf}`: response distributions (unit area, overflow in
    the edge bins) in every bin of `<vs>`, all test objects overlaid, for the variables in `response_binning`;
  * `<plot>_<version>.yaml`: the plot config.

  With [`split_by`](#split-by-reference-categories-split_by) (matched pairs only), in addition:

  * `<plot><tag>_<test obj>_<var>_vs_<vs>_<version>.{png,pdf,json}`: per test object, median and
    resolution of all pairs (black) and per category;
  * `<plot><tag>_<var>_dist_<version>.{png,pdf}`: for the variables in `response_binning`, the response
    distributions per category, integrated over all pairs, one panel per test object;
  * `<plot><tag>_fractions_<version>.json`: per test object, the matched pairs per category
    (`pairs`: counts and fractions) and the summary (median, 16/84% quantiles, resolution, ...) of each
    response for `inclusive`, every category and `other`.

## L1 seed and HLT path efficiencies

  A plot entry with a `path_efficiency:` block gives the per-event efficiency of trigger bits
  (L1 seeds from the GT emulator, HLT paths) vs a reference (gen) quantity
  (`menu_tools/object_performance/path_efficiency.py`, dispatched by `object_performance <config>`):

  ```
  object_performance configs/V50nano/object_performance/path_eff_muons.yaml --version V50nano_170pre6HLT
  ```

  Reference configs: `path_eff_{muons,electrons,taus,jets_sums}.yaml` in `configs/V50nano/object_performance`.

  ```yaml
  IsoMu24PathEff:
    sample: DYLL_M50
    version: V50nano
    reference_object:                  # as in the turn-on configs
      object: "GenPart"
      x_arg: "pt"
      label: "Gen muon, $|\eta| < 2.4$"
      # rank: 2                        # x of the 2nd-highest-pT reference object (default 1: leading)
      cuts:
        object: ["(({statusFlags}>>7)&1) == 1", "abs({pdgId}) == 13", "abs({eta}) < 2.4"]
    path_efficiency:
      L1: [L1_pSingleTkMuon22_final]   # OR of the listed L1 seeds
      HLT: [HLT_IsoMu24_FromL1TkMuon]  # OR of the listed HLT paths
      curves: [L1, HLT, L1_and_HLT, HLT_given_L1]
      labels: {L1: "..."}              # optional legend labels per curve
      plateau_min: 30                  # optional: integrated efficiency for x >= plateau_min
    binning: {min: 0, max: 100, step: 2.5}   # or {edges: [...]}
    xlabel: "Leading gen muon $p_T$ (GeV)"
    ylabel: "Efficiency"
  ```

  **Reference.** Loading and cuts are those of `TurnOnCollection`: `object` cuts, then the leading
  object, then `event` cuts on it; `trafo: HT`/`MHT` (gen HT/MHT from `GenJet`) and `GenMET` are
  event-level. Put the particle selection (pdgId, status) in the `object` cuts to get the leading gen
  muon/electron (in the `*_trigger.yaml` turn-ons it is an `event` cut on the leading `GenPart`).
  `rank: n` takes the n-th highest-pT object instead (e.g. the subleading muon for a double-muon path;
  events with fewer objects drop out).

  **Efficiency.** Per event, without matching to trigger objects: the denominator is the events with a
  reference object in the bin, the numerator those in which the OR of the bits fired. Curves: `L1`,
  `HLT`, `L1_and_HLT` (both fired), `HLT_given_L1` (denominator: events where the L1 OR fired).
  Clopper-Pearson 68% errors. The bits are read directly from the cached per-event records
  `<version>_<sample>_L1.parquet` (`L1_*` fields) and `<version>_<sample>_HLT.parquet` (`HLT_*`),
  row-aligned with the gen parquets. In the Spring24 L1+HLT nanos the HLT bit of an L1-seeded path
  already includes its L1 seed (HLT fired ⇒ seed fired, checked for all reference configs), so `HLT`
  and `L1_and_HLT` coincide; `HLT_given_L1` gives the HLT efficiency relative to L1.

  Outputs, in `outputs/<version>/object_performance/path_efficiency/`: `<plot>_<version>.{png,pdf,json}`
  (json per curve: `label`, `xbins`, `efficiency`, `efficiency_err`, `n_pass`, `n_total`, `plateau`)
  and `<plot>_<version>.yaml` (the plot config).

## Purity, fake rate and multiplicity

  A plot entry with a `purity:` block looks at the trigger objects themselves instead of the gen
  objects (`menu_tools/object_performance/purity_collection.py`, `purity_plotter.py`, dispatched by
  `object_performance <config>`):

  ```
  object_performance configs/V50nano/object_performance/electron_purity.yaml --version V50nano_170X1026
  ```

  Reference configs in `configs/V50nano/object_performance`: `{electron,muons,tau,jets}_purity.yaml`,
  `{electron,muons,tau,jets}_fakerate.yaml`, `photon_purity.yaml` (L1), and
  `hlt_{muon,electron,jets,tau}_purity.yaml` (HLT vs L1, on an L1+HLT cache such as `V50nano_170pre6HLT`).
  They replace the earlier turn-on based `*_purity.yaml` entries, which used the leading L1 object as
  the "reference" and `GenPart`/`GenVisTau` as the "test" object: that gives the purity of the leading
  L1 object only, and their second "test" object (`L1EG`, `L1gmtMuon`, `L1caloTau`) gave an L1-L1
  overlap fraction, not a purity.

  **Objects and matching.** All test objects of each event that pass the object ID / eta cuts of the
  object definition (`leading_only: true`: only the highest-pT one) are kept. A trigger object is
  *matched* if any selected gen object (`reference_gen`) lies within $\Delta R$ < `match_dR` (the test
  object's `match_dR`, unless `purity.match_dR` overrides it). The matching is not exclusive (two
  trigger objects may match the same gen object, e.g. duplicates count as matched). Thresholds are on
  the online `pt` field, `pt >= threshold` as in the rate plots (no offline scalings).

  **Definitions.**

  | mode | quantity (file name) | definition | vs |
  |---|---|---|---|
  | `purity` | `purity` | N(matched objects) / N(objects), Clopper-Pearson 68% | pt, eta, abseta, phi, pu |
  | `fake_rate` | `fake_fraction` | N(unmatched) / N(objects) = 1 - purity | pt, eta, abseta, phi, pu |
  | `fake_rate` | `unmatched_per_event` | mean number of unmatched objects with pT >= thr per event, error std/sqrt(N) | threshold, pu |
  | `fake_rate` | `event_fraction` | fraction of events with >= 1 unmatched object with pT >= thr (CP; x 31038 kHz if `rate`) | threshold, pu |
  | `fake_rate` | `unmatched_density` | unmatched objects with pT >= thr per event per bin (Poisson) | eta, abseta, phi |
  | `multiplicity` | `objects_per_event` | mean number of objects with pT >= thr per event (no gen matching) | threshold, pu |
  | `multiplicity` | `event_fraction` | fraction of events with >= 1 object with pT >= thr; x 31038 kHz (`RATE_NORM_FACTOR`) if `rate` | threshold, pu |
  | `multiplicity` | `density` | objects with pT >= thr per event per bin | eta, abseta, phi |

  The vs-pt plots use all objects (no threshold); the vs eta/phi/pu plots are made for each of
  `thresholds`. The event-level quantities vs pileup also get a weighted straight-line fit (slope per
  pileup interaction in the legend and the json).

  *Minimum bias.* The gen record of the minimum-bias samples is pruned (no `GenPart`/`GenJet` in the
  caches), so a gen-based fake rate is not defined there. The `multiplicity` mode gives the
  well-defined, gen-independent quantity: the per-event multiplicity of trigger objects above
  threshold and the rate of events with >= 1 such object in kHz (`rate`, default true for samples
  named `MinBias*`), vs threshold and pileup. In minimum bias essentially every object above a few GeV
  is a fake / pileup object, so this is the fake rate the trigger sees; at a given threshold the
  `event_fraction` in kHz is the single-object rate of the rate plots.

  *Jets.* The usual definition of fake (pileup) jets is used: L1 jets with no `GenJet` (pT > 10 GeV)
  within `match_dR`. `GenJet`s are clustered from the hard-scatter particles only, so pileup jets are
  unmatched.

  *Signal samples.* Gen leptons: last copy (`statusFlags` bit 13) and prompt (bit 0) or from a prompt
  tau decay (bit 3), so that $Z \to \tau\tau \to e/\mu$ in DY counts as real. Unmatched objects in
  signal samples are not all "fakes": in DY the unmatched high-pT L1 electrons sit mostly at
  $\Delta R$ = 0.2-0.45 from the gen electron or on a gen photon (brem / FSR duplicates).
  `Pileup_nTrueInt` is constant (200) in the Spring24 samples: bin in `nPU`.

  ```yaml
  ElectronsFakeRate:
    sample: DYLL_M50
    version: V50nano
    test_objects:                      # all overlaid; obj:id[:eta_range] as usual
      L1tkElectron:NoIso: "pt"
      L1tkElectron:Iso: "pt"
    purity:
      mode: fake_rate                  # purity | fake_rate | multiplicity
      reference_gen:                   # not for multiplicity; a list of such entries is an OR
        object: GenPart                # parquet name, or an object key with id ("GenPart:electron")
        label: "prompt gen e"
        cuts: ["abs({pdgId}) == 11", "(({statusFlags}>>13)&1) == 1"]
      # match_dR: 0.15                 # default: the test object's match_dR
      vs:
        pt: {edges: [0, 5, 10, 20, 30, 50, 100]}   # trigger-object pT
        eta: {min: -2.4, max: 2.4, step: 0.2}       # trigger-object eta (abseta, phi too)
        pu: {edges: [140, 170, 185, 195, 205, 215, 230, 260]}
        threshold: {min: 0, max: 60, step: 2}       # threshold scan (event-level quantities)
      thresholds: [10, 20, 30]         # for the vs eta/phi/pu plots (default [0])
      leading_only: false
      # rate: true                     # event fractions in kHz (default: MinBias samples)
      # pu_variable: nPU
      # pileup_version: V50nano_170X1026PU
  ```

  **Pileup.** The `pu` binning reads `<v>_<sample>_Pileup.parquet` from `pileup_version` if given,
  else from the plot version `<v>`, else from `<v>PU` (e.g. the row-aligned `V50nano_170X1026PU`
  cache next to `V50nano_170X1026`); the event count must match. Without it the `pu` plots are
  skipped with a warning (e.g. `MinBias` of `V50nano_170X1026`: run the `*_fakerate.yaml` configs on
  `V50nano_dev170pre6HLT`, whose minimum bias has `Pileup`, for the multiplicity vs nPU). Plot
  entries whose sample is missing in the version (e.g. `MinBias` in `V50nano_170pre6HLT`) are skipped
  with a warning.

  Outputs, in `outputs/<version>/object_performance/purity/`:
  `<plot>_<quantity>_vs_<vs>[_thr<t>]_<version>.{png,pdf,json}` (all test objects overlaid; json per
  object: `label`, `match_dR`, `edges`/`xbins` or `thresholds`, `y`, `err_lo`, `err_hi`, `num`,
  `den`, and `integral` (all objects) or `fit`; plus `definition`, `n_events`, `pileup_source`) and
  `<plot>_<version>.yaml` (the plot config).

## b-tagging efficiency and mis-identification

  A plot entry with a `btag:` block gives the b-tagging efficiency and the c / light / pileup
  mis-identification rates of L1 and HLT jets, and ROC curves from the continuous discriminant
  (`menu_tools/object_performance/btag_collection.py`, `btag_plotter.py`, dispatched by
  `object_performance <config>`):

  ```
  object_performance configs/V50nano/object_performance/btag_tt.yaml --version V50nano_170pre6HLT
  ```

  Reference configs: `btag_tt.yaml` (TT, where the L1 working points are defined) and
  `btag_hh4b.yaml` (HHTo4B), comparing `L1puppiJetSC4NG` (NG tagger `bTagScore`) with
  `hltAK4PuppiJetCorr` (DeepFlavour, JEC-corrected pT). The working points are ids of the jet
  objects, see [objects](objects.md#b-tagging-working-points).

  **Jets and truth.** All reco jets of each event passing the test object's id cuts and
  |eta| < `max_abs_eta` are used. The closest `GenJet` (after the `reference_gen` cuts, default
  pT > 10 GeV) within `match_dR` gives the flavour from `hadronFlavour`: b (5), c (4), light (0).
  Jets with no `GenJet` within `pu_dR` are *pileup* jets (`GenJet`s are clustered from the
  hard-scatter particles only). Jets with a `GenJet` between `match_dR` and `pu_dR` but none
  within `match_dR` are not used. Two reco jets may match the same `GenJet`.

  **Definitions.** A jet is *tagged* at a working point if it passes the cuts of the
  working-point id (an id of the same object). For each flavour: N(tagged jets) / N(jets), i.e.
  the tagging efficiency of b jets and the mis-identification rates of c, light and pileup jets,
  **conditional on the reco jet existing** (and passing the |eta| cut): the jet reconstruction
  efficiency is not included. Clopper-Pearson 68% intervals.

  ```yaml
  BTagTT:
    sample: TT
    version: V50nano
    test_objects:
      L1puppiJetSC4NG:default: "pt"
      hltAK4PuppiJetCorr:default: "pt"
    btag:
      discriminants:                   # per test object: expression, or {name: expression}
        L1puppiJetSC4NG:default: "{bTagScore}"
        hltAK4PuppiJetCorr:default:
          "prob(b)": "{DeepFlavour_prob_b}"            # the first one is the main one
          "b+bb+lepb": "{DeepFlavour_prob_b} + {DeepFlavour_prob_bb} + {DeepFlavour_prob_lepb}"
      working_points:                  # ids of the same object (or full keys obj:id)
        L1puppiJetSC4NG:default: [bTagLight10, bTagLight1, bjetnn]
        hltAK4PuppiJetCorr:default: [bTagDeepFlavour0p275, bTagDeepFlavour0p375, bTagLight10]
      reference_gen: {object: GenJet, label: "GenJet", cuts: ["{pt} > 10"]}   # default
      flavour_field: hadronFlavour     # default
      match_dR: 0.2                    # default: the test object's match_dR
      pu_dR: 0.4                       # default 0.4
      max_abs_eta: 2.4                 # default 2.4
      min_pt: 30                       # reco pT cut of the vs eta / |eta| / pu plots (default 30)
      flavours: [b, c, light, pu]      # default: all
      vs:
        pt: {edges: [20, 30, 50, 100, 200, 500]}     # reco-jet pT (no pT cut)
        genpt: {edges: [20, 30, 50, 100, 200, 500]}  # matched GenJet pT (not for pileup)
        eta: {min: -2.4, max: 2.4, step: 0.3}        # reco-jet eta (abseta: |eta|)
        pu: {edges: [140, 170, 185, 195, 205, 215, 230, 260]}
      roc:
        pt_bins: [[30, 100], [100, null], [30, null]]   # reco-jet pT bins, null: no upper edge
        against: [light, c, pu]
        # eta_region: [0, 1.5]         # optional |eta| range of the ROC jets
        target_misid: {light: [0.1, 0.01]}   # discriminant thresholds at these mis-id rates
      summary:
        pt_bins: [[30, 100], [100, null]]
        eta_regions: {inclusive: [0, 2.4], barrel: [0, 1.5]}
      # pu_variable: nPU               # pileup binning, as for purity (pileup_version too)
  ```

  The pT binning uses the `pt` field of each object: the online pT for L1 jets (no offline
  scalings) and the corrected pT for `hltAK4PuppiJetCorr`. The vs `genpt` plots compare L1 and
  HLT at the same true jet pT.

  **ROC curves.** In each reco pT bin, b efficiency vs mis-id rate of the `against` flavour for a
  scan of the discriminant (all distinct values, e.g. the 1/128 grid of the L1 scores, or 400
  quantiles), all objects and discriminants overlaid; the working points are drawn as markers with
  their measured (b eff., mis-id) and errors. With `target_misid` the json lists, per object and
  discriminant, the smallest threshold t among the score values with mis-id(score > t) <= target,
  and the b efficiency there (this is how the L1 working points were defined).

  Outputs, in `outputs/<version>/object_performance/btag/`:

  * `<plot>_<flavour>_vs_<vs>_<version>.{png,pdf,json}`: efficiency (b) or mis-id rate vs `<vs>`,
    one curve per object and working point; json per curve `label`, `edges`, `xbins`, `y`,
    `err_lo`, `err_hi`, `num`, `den`;
  * `<plot>_roc_<against>_pt<lo>to<hi>_<version>.{png,pdf,json}`: ROC curves (json: per curve the
    `threshold`, `eff_b`, `misid` arrays; per working point `eff_b`, `misid` and errors;
    `target_misid`);
  * `<plot>_summary_<version>.{json,txt}`: all rates in the `summary` pT bins and eta regions, and
    the number of jets per truth category;
  * `<plot>_<version>.yaml`: the plot config.

  **Caveats (V50nano_170pre6HLT).**
  * The HLT b-tag filters (`HLTPFJetTag`) cut on DeepFlavour **prob(b) alone**
    (`hltPfDeepFlavourJetTagsModEta2p4:probb`), not on b + bb + lepb; the HLT working points do the
    same. b + bb + lepb is shown as a second ROC curve.
  * The nano scores are from `hltPfDeepFlavourJetTags` (run by `DST_PFScouting`, i.e. stored in
    all events), the same model as in the b-tag paths but run on the uncorrected
    `hltAK4PFPuppiJets` (the paths run it on the corrected jets with pT > 30 GeV, |eta| < 2.4).
    The jet pT is a tagger input, so the stored scores are close to, but not exactly, the ones
    the paths cut on.
  * The L1 `bTagScore` is quantized in steps of 1/128 and depends strongly on the jet pT: a fixed
    cut gives a strongly pT-dependent mis-id rate.
  * `GenJet`s have pT > 10 GeV in the nano: a reco jet next to a softer hard-scatter jet counts
    as pileup.

  Tests: `menu_tools/object_performance/tests/test_btag.py`.
